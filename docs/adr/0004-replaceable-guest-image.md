# ADR-0004: 안드로이드 게스트는 이미지 프로필로 교체되는 부품이다

상태: 채택, 2026-09-26.

## 배경

사용자 요구(2026-09-26 밤): "Pie → 13 → 15 → 16 → 17을 지원하는 것이 1차 목표이며, 이후
유지보수에서도 최신이 나오는 족족 최대한 쫓아가는 것이 목적입니다. 즉, 안드로이드는 애초에
교체 가능하게 설계되어야 합니다." D2는 Bliss 16.9.x(안드로이드 13)를 1차, Bliss 18 또는 arcadia
자체 빌드를 2차로 정했고, D4와 6절은 변환기를 교체 가능한 부품으로 만들었다. 게스트 이미지에는
그런 계약이 없었고, 런처는 Bliss 16.9.7 하나를 전제로 명령과 부팅 인자를 박아 두었다(예:
`cmd media_session volume`, virgl GRUB 항목, `edid=off`).

## 결정

1. 게스트 이미지는 `manifests/images/<id>.json`의 **게스트 이미지 프로필**로 선언한다. 프로필은
   산출물 이름, 안드로이드 버전과 API 레벨, 배포 계열, 변환기 종류, 부팅 인자와 GRUB 힌트,
   설치 안내 문장, 허용 목록 안의 QEMU 재정의, 검증 상태를 갖는다. 산출물 URL과 SHA-256은
   그대로 `manifests/artifacts.json`에 있다(R2).
2. 안드로이드 세대에 따라 달라지는 게스트 대화(앱 목록, 볼륨, 기기 ID, 전경 앱, 부팅 표지,
   네이티브 브리지 속성, 화면 명령)는 `ome-guest-image`의 **세대 어댑터**가 소유한다. `ome-adb`는
   세션이고 어댑터가 방언이다. 다른 어떤 크레이트도 API 레벨로 분기하지 않는다.
3. 게스트를 처음 부팅한 뒤 **능력 조사**가 제품이 기대는 능력을 실제로 시험해 게스트 메타데이터에
   적는다. 조사되지 않은 능력은 화면에 없는 버튼이다. 모르는 API 레벨은 가장 새 어댑터로 시작해
   조사로 확정한다.
4. 새 안드로이드 버전을 지원하는 절차는 프로필 파일 추가, 필요할 때만 어댑터 추가, 능력 조사
   통과, `docs/evidence/M2/images/<id>.md` 기록, 호환성 항목 갱신이다. 이 절차 밖의 코드 변경이
   필요하면 이 ADR을 다시 연다.
5. 1차 목표 프로필은 안드로이드 9(Pie), 13, 15, 16, 17이다. 안드로이드 13(Bliss 16.9.7)은 M0과
   M1로 검증되었다. 나머지는 후보 이미지를 확인한 뒤 프로필을 만든다(`docs/ARCHITECTURE.md`
   3.15절). Pie는 `minSdk`가 28을 넘는 앱을 설치할 수 없고 변환기가 libhoudini다. 그 사실은
   호환성 항목이 말한다.
6. v1은 한 번에 게스트 하나를 돌린다(D9). 다른 세대의 게스트를 여러 개 만들어 두고 골라 시작할
   수는 있다. 동시 실행은 D9에 따라 없다.

## 결과

- D2의 "1차 Bliss 16.9.x, 2차 자체 빌드"는 프로필 두 개의 이야기가 되고, 그 사이의 다른 세대도
  같은 방식으로 들어온다. D2의 본문은 이 ADR을 가리키도록 고쳤다.
- 마법사 S1.4는 이미지를 고르는 단계가 된다. 설정에 게스트 이미지 관리가 생긴다.
- 런처(PowerShell)는 바꾸지 않는다. M0과 M1 도구는 Bliss 16.9.7 전용으로 남고, 제품은 프로필로
  간다.
- QEMU 재정의는 열거형 값의 허용 목록으로 제한한다. 프로필이 임의 명령줄을 싣는 통로가 되지
  않도록 `ome-guest-config`가 검증한다.
