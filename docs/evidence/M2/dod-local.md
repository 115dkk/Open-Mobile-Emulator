## 인계 문서 3절의 실기 확인 (26회차 기록으로)

`handoff-20260930.md` 3절이 개발 PC에서 볼 것으로 남긴 제품 고침 다섯 가지 가운데 네 가지는 26회차의 기록으로 답한다.

- 콘솔 창 깜박임: 드라이버는 키를 보낼 때마다 전경 창을 12번 표본 조사해 다른 창을 `others`에 적는다. 26회차의
  키 입력 29회 모두 `others`가 비어 있었다. 게스트가 도는 동안 전경을 뺏는 창은 없었다.
- 키 순서: 설치기의 키 29회가 모두 첫 시도에 도착했다(`grub-enter-retry`, `foreground-unsettled` 없음). 잰 유지
  시간은 아래 절에 있다.
- 오디오와 GL 대체 경로: 설치기와 첫 부팅의 QEMU 명령줄 둘 다 `-audiodev dsound,id=snd0`이고 스냅숏의 `gpuMode`는
  내내 `virgl`이었다. RTX 2080 SUPER에서는 둘 다 발동하지 않는다.
- 호스트 점검 문구: 26회차 결과의 호스트 점검 8행이 통일된 문구("켜져 있습니다.", "필요하지 않습니다.", "설치에
  충분한 여유가 있습니다.")로 나왔다.
- 설치기 실패 시 `설치 완료` 막기: 설치기가 실패한 회차가 없어 실기로는 보지 못했다. 단위 테스트로만 확인된 상태다.

같은 문서 4절 3번(10회차의 굳는 창 질문)은 원인이 밝혀져 답이 필요 없어졌다. `embedded-display-freeze.md`의 원인
절과 위 13회차 행에 있다.

## 27회차 굳음의 재현 시도와 그 김에 드러난 결함 (2026-10-01 07:14)

28회차가 남긴 홈(설치된 게스트와 게임)으로 제품을 다시 띄워 게스트를 켠 뒤, 사람이 다른 창을 쓰는 것을 흉내 냈다.
문자표 창을 무대 위에 띄워 여섯 번 끌고, 최소화했다 되살려 전경을 가져가게 하고, 제품 창을 최소화했다 되살리는
한 바퀴를 세 번 돌리는 동안 1초마다 제품의 스냅숏 명령 응답 시간을 쟀다. 세 바퀴 모두 응답은 최대 24 ms였고
QMP도 멈추지 않았다. 27회차와 다른 점은 게스트가 첫 부팅 직후가 아니라 설치된 상태로 부팅한 뒤였다는 것, 그리고
27회차에서 열린 앱(Claude 데스크톱, VST3 오디오 도구)이 문자표보다 무겁다는 것이다. 굳음은 재현되지 않은 채
남는다. 도구(제품을 홈으로 띄우는 드라이버, 창 흔들기 도우미, 멈추면 두 프로세스의 미니덤프를 남기는 도우미)는
세션 스크래치패드에 있다.

이 시도가 다른 결함을 드러냈다. 마법사를 끝낸 홈으로 제품을 다시 띄우면 마법사가 1단계부터 다시 뜬다.
런타임이 시작할 때마다 `WizardState::default()`와 `AppPhase::Wizard`로 출발하고 마법사 상태를 어디에도 저장하지
않기 때문이다. 계약(`docs/ARCHITECTURE.md` 8.7의 `wizard_defer`, `docs/M2-SCREENS.md` S1의 `나중에 하기`)은
진행 상태를 저장해 다음 실행에서 잇는다고 되어 있다. 고침은 `state.json`에 마법사 상태를 함께 저장하고 시작할
때 되살리는 것이다(워커 W1). 재현 스크립트는 그동안 `나중에 하기`로 마법사를 닫고 무대로 갔다.

## 회차마다 배운 것

- 이 PC의 Windows OCR은 200 % 배율의 1744×1216 캡처에서 파란 글자와 강조된 줄을 자주 빼먹고, 대화상자의 제목
  (`Question`, `Confirm`)을 세 가지쯤으로 읽으며, 프롬프트 줄을 표의 열 사이에 끼워 넣는다. 분류 규칙은 제목이
  아니라 본문 문장에 걸고, 표는 열 순서를 가정하지 않는다.
- 제품의 부팅 시한(180초)은 설치기 세션에 걸리면 안 된다. 17·18회차에서 정지 요청이 나간 순간부터 웹뷰가 키를
  넘기지 않았고(게스트가 실행 중이 아니라고 보므로) 30초 뒤 QEMU가 꺼졌다. 17회차의 "정말 vda1을 ESP로?"
  대화상자에 No가 눌린 것처럼 보였던 것은 이 정지였다.
- 예/아니오 상자는 Enter 대신 dialog의 y·n 단축키로 답한다. 강조된 단추가 무엇이든 답이 같다.
- ESP 파일 시스템 목록의 'Do not re-format'은 갓 만든 파티션에도 있다. 포맷 여부는 목록이 아니라 지나온 화면
  (포맷 확인, 마운트 실패 뒤 포맷)으로 기억한다.
- 게임을 처음 띄우면 안드로이드 13이 알림 권한을 묻는다(`POST_NOTIFICATIONS`). 드라이버는 이 운영체제 대화상자에만
  Allow로 답하고 게임 화면에는 손대지 않는다. Allow인 까닭은 M0 기록(`../M0/findings-20260926.md` 3번)에 있다.
  거부하면 게임의 자료 내려받기 서비스가 전경 알림을 띄우지 못해 죽었고, 보통 사용자처럼 허용해 해결했다. 누르는
  자리는 게스트 캡처의 OCR 줄 좌표(1280×800 기준 `Allow`가 622,393 크기 36×11)를 비율로 바꿔 SDL 창에 마우스로
  보낸다. SDL이 창 안 위치를 usb-tablet 절대 좌표로 옮기므로 무대 크기나 배율과 무관하다.
- 게임 캡처를 영어 OCR로 읽으면 첫 화면(검은 바탕에 아이콘)은 글자가 없고, 제목 화면과 다운로드 안내에는 `EPIDGames
  All rights reserved`가, 다운로드 안내에는 크기(`5.1GB`를 `S.IGB`로 읽음)와 `ON`, `OFF`, `Wi-Fi`가 읽힌다. 한글은
  이 엔진이 읽지 못한다. 드라이버의 판정은 이 낱말들에 건다.
- 14회차의 cfdisk 종료는 설명되지 않았다. 15회차의 입력 추적으로 잰 누름·뗌 간격은 QMP 결과 기준 71~184 ms라
  커널의 반복 지연(250 ms)에 못 미친다. 같은 열쇠 순서가 15~19회차에서는 다섯 번 모두 통과했다.

## 키 유지 시간 측정 (2026-10-01 02:32, `key_hold_real`)

14회차의 cfdisk 종료를 게스트 쪽 키 반복으로 의심해, 제품의 키 경로(웹뷰 → 런타임 → 감독자 큐 → QMP `input-send-event` →
usb-kbd)로 40 ms 누른 키를 60번씩 보내고 게스트의 `getevent -ltq` 시각으로 누름과 뗌을 짝지어 쟀다. 대상은 개발 게스트
`default`(안드로이드 13, 부팅 뒤)다.

| 계열 | 표본 | 게스트 유지 시간 min / p50 / max (ms) | 250 ms 이상 | REPEAT | 짝 없는 DOWN |
|---|---|---|---|---|---|
| Enter, 유휴 | 60 / 60 | 18.8 / 42.2 / 120.1 | 0 | 0 | 0 |
| KeyA, 유휴 | 60 / 60 | 11.7 / 47.6 / 85.7 | 0 | 0 | 0 |
| Enter, vCPU 넷과 디스크 쓰기 부하 | 60 / 60 | 8.7 / 46.4 / 100.3 | 0 | 0 | 0 |

호스트가 보낸 간격은 40~120 ms였다. 게스트가 본 유지 시간은 커널의 반복 지연(250 ms)에 한 번도 닿지 않았고 반복 이벤트도
없었다. 그러므로 14회차의 cfdisk 종료는 키 반복이 아니며, 원인은 아직 모른다. 이 측정은 `cargo test -p ome-runtime --test
key_hold_real -- --ignored --nocapture`로 다시 돌릴 수 있다(105초).
