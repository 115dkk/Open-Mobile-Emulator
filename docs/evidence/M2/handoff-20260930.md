# 인수인계: 러너 완료 실행에서 개발 PC로 (2026-09-30)

이 문서는 클라우드 세션(세션 링크는 PR #4 본문 끝)이 개발 PC 쪽에 공을 넘기며 남긴다. 사용자 결정
2026-09-30: "러너 M2가 증명되거나 신호를 주면 개발 PC로 넘긴다"였고, 39회 뒤에 신호가 왔다.

## 1. 지금 상태

- 브랜치 `ccr-4ddf4024-unn46m`, PR #4(열림, `main` 기준 32개 커밋 안팎). 일반 CI(checks, host, host-licenses,
  forbidden-patterns-linux)는 최신 헤드에서 초록이다. `wizard` 검사(완료 실행)는 끝까지 간 회차가 없어 빨갛다.
- 회차별 사실과 판단은 `docs/evidence/M2/dod-ci.md`(16~39회)와 `dod-ci/runNN/`에 있다. 각 회차의 첫 문단이
  어디까지 갔는지, 둘째 문단이 원인, 셋째가 고침이다.
- 개발 PC의 마지막 상태는 지역 10회차(3초 표시와 GRUB 전환이 겹칠 때 굳는 창을 QMP 숨김·표시로 살리는지 확인
  중)였고, 그 회차의 코드는 PC에 남지 않았다. 밀린 상태는 9회차였다.

## 2. 러너가 증명한 것 (39회까지)

윈도우 2025 러너, WHPX, 표준 VGA(소프트웨어 렌더링), 오디오 없음, 100% 배율, 표준 사용자 `omeuser`로 제품을 띄워:

- 마법사 S1.1~S1.4: 호스트 점검 8행 준비, WHPX 건너뜀, ISO 내려받기(2.43 GB, 22~60 MB/s)와 SHA-256 검증.
- S1.5: 디스크 생성, 설치기 QEMU 기동, GRUB 메뉴 인식(바닥줄), 선택 막대 판독으로 `Installation` 이동과 Enter 확인,
  설치기의 안내 상자와 파티션 목록 구분, cfdisk 전체(gpt, 512M EFI System, 나머지 Linux filesystem, 쓰기, 종료),
  설치기 대화 상자 순환의 ESP 선택과 fat32 선택까지(39회). 그다음 "drive name" 질문의 분류 규칙을 고쳤으나
  러너에서 돌려 보지 못했다. 그 뒤(포맷 확인, ext4, OTA 거부, GRUB2, 복사, 완료, 첫 부팅, 앱 설치, 게임 실행)는
  드라이버가 아직 실제로 지나 본 적이 없다.
- 러너에서 재현되지 않는 것: GPU 경로 전부(virgl, 패치 0005 창 담기, 10회차의 굳는 창), 오디오, 같은 사용자의
  트레이 아이콘(`종료` 메뉴는 러너에서 열리지 않아 창 닫기로 대신한다).

## 3. 이 PR에 든 제품 고침 (개발 PC에서 실기로 확인할 것)

| 고침 | 왜 | 실기에서 볼 것 |
|---|---|---|
| adb, qemu-img, QEMU를 `CREATE_NO_WINDOW`로 띄움 (`ome-adb`, `ome-runtime/operations.rs`, `ome-platform-win/ffi/process.rs`) | 창 있는 앱의 콘솔 자식은 콘솔 창을 띄워 전경을 뺏고 게스트 창을 덮었다(36회). 부팅 폴링의 adb가 몇 초마다 그랬다 | 게스트가 도는 동안 콘솔 창이 깜박이지 않는지, QEMU 뒤에 콘솔 창이 없는지 |
| `useGuestKeyboard`가 키 이벤트를 큐로 하나씩 순서대로 보냄 | 1 ms 간격의 누름·뗌이 별도 블로킹 작업으로 돌아 뗌이 누름을 앞질렀다(30·35회) | 게스트에 타자할 때 글자 누락이나 눌린 채 남는 키가 없는지 |
| 마법사 S1.5는 설치기 QEMU가 실패 상태면 `설치 완료`를 막고 `다시 설치`를 보임 | 게스트 기록만 있으면 켜져 빈 디스크로 넘어갈 수 있었다(21·26회) | 설치기가 시작에 실패했을 때의 무대 문구와 단추 |
| 오디오 장치 0이면 QEMU 오디오 백엔드 `none`, OpenGL이 GDI Generic이면 시작 시 소프트웨어 렌더링 저장과 알림 | 러너에는 둘 다 없다(21·22회) | RTX 2080 SUPER에서는 둘 다 발동하지 않아야 한다(virgl 유지, dsound 유지) |
| 호스트 점검 문구 통일(`Windows 다시 시작`, `디스크 공간`, "필요하지 않습니다." 등) | 사용자 지시 2026-09-30 | 첫 화면 |

## 4. 개발 PC에서 할 일 (순서 제안)

1. PR #4를 읽고 병합하거나 그 브랜치에서 계속한다. 새 커밋은 같은 브랜치에 얹으면 PR이 따라온다.
2. 실기 완료 실행. 첫 걸음은 러너에서 못 돌린 분류 규칙 고침(39회 뒤 커밋)을 확인하는 것이다. 러너를 한 번 더
   띄워도 되고(5번), 실기로 바로 가도 된다. `host/`에서 제품을 빌드한 뒤 `node ci/dod/run-dod.mjs`를 돈다. 환경 변수는 `OME_HOME`(빈 새 홈),
   `OME_DOD_APP`(ome.exe 경로), `OME_DOD_GAME_APK_DIR`(pulled.json과 split APK 네 개), `OME_DOD_OUTPUT`(증거 폴더),
   선택으로 `OME_DOD_DEADLINE_MIN`(기본 100), `OME_DOD_QEMU_DIR`, `OME_DOD_SDL_KEYS=1`(예전 SDL 키 경로, 권하지 않음).
   키는 이제 제품 창으로 들어가 QMP로 가고, GRUB 선택과 cfdisk 단계는 화면으로 확인하며 움직인다. 200% 배율에서도
   판독기가 같은 답을 내는 것을 개발 PC 프레임으로 확인해 두었다(`dod-ci/run32/grub-highlight-mock-test.ps1`).
   개발 PC는 GPU가 있으므로 첫 부팅은 GRUB 기본 항목(virgl)으로 간다(`first-boot-default`).
3. 10회차의 질문. 3초 표시와 GRUB 전환이 겹칠 때 굳는 창이 QMP 숨김·표시로 살아나는지. 러너로는 답할 수 없는
   유일한 M2 항목이다. `docs/evidence/M2/embedded-display-freeze.md`가 출발점이다.
4. M2 완료 기준 1의 증거는 실기(GPU) 완주로 만든다. 러너의 완주는 소프트웨어 렌더링 경로의 증거로 `dod-ci.md`에 남긴다.
   완료 기준 2(R9·R10 코드 검색)는 끝났다(`docs/evidence/M2/r9-r10-code-search.md`).
5. 러너를 다시 돌리려면 GitHub Actions에서 `m2-dod.yml`을 `workflow_dispatch`로 띄운다(비밀 `OME_FIXTURES_DEPLOY_KEY`
   필요). 증거는 `m2-wizard-evidence` 아티팩트로 나오고, 실패 시 `shots/failure.png`와 `driver-output.txt`부터 본다.
   러너의 한계: GPU 없음, 오디오 없음, 100% 배율, 중첩 가상화 지터(키 반복은 제품 키 경로로 해결됨), 회차당 약 15분.

## 5. 남은 결정과 다음 마일스톤

- 사용자 결정 대기: 출시 후 트랙 우선순위(8절 6번), D8 재개 여부(8번), 구글 번역기 사용 범위(9번). 코드 서명은
  하지 않기로 정했고(3번, 2026-09-30) 무료 후보 SignPath Foundation과 페이트론 `FUNDING.yml`은 CLAUDE.md에 적었다.
- M3의 CI 절반(러너에서 QEMU 빌드와 `actions/attest`, `qemu-source-offer`, THIRD_PARTY·NOTICE 검사, 설치기 빌드)은
  클라우드 세션이 할 수 있는 일이고, GPU 증거와 P1 조사는 실기가 있어야 한다.

## 6. 이 세션이 정리한 것

PR 활동 구독을 끊고 한 시간 점검 루틴을 지웠다. 감시 중이던 러너는 없다. 작업 트리는 비어 있고 모든 커밋이 밀려 있다.

## 7. 후속 (2026-10-01, 개발 PC)

개발 PC의 회차 11~28은 `dod-local.md`에 있다. 4절 2번의 실기 완료 실행은 28회차에서 마법사부터 게임의 데이터
다운로드 안내까지 통과했고(깨끗한 QEMU 빌드, 드라이버가 스스로 `passed`), 이것이 4절 4번이 요구한 M2 완료 기준
1의 실기(GPU) 증거다. 4절 3번의 굳는 창 질문은 원인이 밝혀져(`embedded-display-freeze.md` 원인 절, 숨은 콘솔 창의
GL 컨텍스트 전환 실패, 고침은 `-serial none -parallel none`) 답이 필요 없어졌다. 3절의 제품 고침 다섯 가지 가운데
네 가지는 26회차 기록으로 확인했고 설치기 실패 시의 `설치 완료` 막기만 실기로 볼 기회가 없었다(`dod-local.md`
"인계 문서 3절의 실기 확인"). 새로 남은 물음은 27회차의 굳음이다. 게스트가 도는 동안 사용자가 다른 창을 열자
QEMU가 QMP에 답하지 않았고 제품이 따라 굳었다. 한 번뿐이고 원인은 미상이다.
