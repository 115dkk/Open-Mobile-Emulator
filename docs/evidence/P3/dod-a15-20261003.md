# 안드로이드 15 프로필의 완료 실행 (2026-10-02~03)

`ome-android-15`(candidate) 프로필로 제품의 마법사를 처음부터 돌린 기록이다. 드라이버는 `ci/dod/run-dod.mjs`이고
`OME_DOD_IMAGE=ome-android-15`, `OME_DOD_SKIP_GAME=1`(첫 부팅과 능력 조사까지만)로 돌렸다. 새 홈에는 빌드한 ISO를 릴리스 파일
이름(`ome-android-15-x86_64-20261002-db973c9.iso`)으로 하드 링크해 두어 내려받기를 건너뛰었다.

## 2. `/adb_keys`는 심볼릭 링크다 (a15-4)

빌드한 `system.img`의 루트를 `debugfs`로 보면 `/adb_keys`는 30바이트짜리 빠른 심볼릭 링크이고 대상
`/product/etc/security/adb_keys`는 이미지에 없다(`/system/product/etc/security`가 없음). 그래서 이미지를 루프 마운트해
`cp`하면 링크를 따라가다 실패한다. 그리고 시스템 이미지는 실행 중에 읽기 전용으로 붙으므로 `init.rc`의
`restorecon /adb_keys`가 라벨 없는 파일에 라벨을 붙여 줄 수 없다.

`plat_file_contexts`의 해당 항목은 다음과 같다.

```
/adb_keys           u:object_r:system_file:s0
/(product|system/product)/etc/security/adb_keys                 u:object_r:adb_keys_file:s0
```

고친 도우미(aaropa 길)는 이미지를 마운트하지 않는다. `install.sfs`의 `debugfs` 1.47.2로 링크를 지우고 일반 파일을 쓰고,
`security.selinux`에 `u:object_r:system_file:s0\0`을 넣는다. `debugfs`는 요청이 실패해도 0으로 끝나므로 쓴 뒤 종류, 라벨,
내용을 다시 읽어 확인한다. 같은 명령을 WSL에서 빌드 산출물 `system.img`의 복사본에 돌린 결과다.

```
Inode: 13   Type: regular    Mode:  0644   Flags: 0x80000
User:     0   Group:     0   Project:     0   Size: 28
Extended attributes:
  security.selinux (26) = "u:object_r:system_file:s0\000"
QAAAAKEY1 a@b
QAAAAKEY2 c@d
```

`e2fsck -fn`은 오류 없이 끝났다(`18370/305216 files`).

## 3. 키는 통하고, adb가 꺼진 채 출시된다 (a15-5)

a15-5의 설치 직렬 로그 끝부분이다.

```
OME-INSTALL step keys 91
OME-INSTALL keys 1
OME-INSTALL step finish 92
OME-INSTALL done
```

첫 부팅 화면은 잠금 화면까지 갔는데 제품은 `bootCompleted`를 끝내 보지 못했다(스냅샷 235개 전부 `adbConnected:false`).
부팅 시한이 지나면 제품이 `system_powerdown`을 보내고(화면에 전원 메뉴가 뜸) 다시 띄우기를 세 번 되풀이했다.

같은 디스크를 제품의 명령줄 그대로, 직렬 포트만 TCP로 열고 `console=ttyS0 androidboot.enable_console=1`을 더해 손으로
띄우고 루트 콘솔에서 확인한 값이다.

```
sys.boot_completed      1
init.svc.adbd           stopped
ro.adb.secure           1
persist.sys.usb.config  none
sys.usb.config          mtp
ro.build.type           user
ro.debuggable           0
settings global adb_enabled  0

-rw-r--r-- 1 root root u:object_r:system_file:s0  727 2026-10-03 02:24 /adb_keys
```

콘솔에서 `settings put global adb_enabled 1`을 하자 `init.svc.adbd=running`, `sys.usb.config=adb`가 되고 adbd가 5555에서
듣기 시작했다. 호스트에서는 승인 창 없이 바로 승인되었다.

```
connected to 127.0.0.1:5555
127.0.0.1:5555  device product:Standard PC (Q35 + ICH9, 2009) model:Generic_Android_x86_64 device:x86_64 transport_id:562
$ adb shell getprop ro.build.version.release
15
```

따라서 키 주입(ADR-0012 결정 4)은 성립한다. 남은 문제는 이 이미지가 `user` 빌드처럼 adb를 끈 채 나온다는 점이다. 10-02의
라이브 부팅에서 adbd가 5555를 들었던 것은 부팅 인자 때문이 아니다(라이브 인자 `androidboot.live=true`는
`UsbHostManager`의 대용량 저장 장치 처리에만 쓰이고, initrd의 `/init`에서는 루트 찾기에만 쓰인다). 빌드한 `system.img`의
`build.prop`에는 `persist.sys.usb.config` 줄이 없다.

## 4. adb를 기본으로 켜고 완주 (a15-6)

도우미가 키를 넣은 뒤 같은 `debugfs` 방식으로 `/system/build.prop`에 `persist.sys.usb.config=adb`를 덧붙이게 했다(원래 모드
0600과 라벨 `system_file` 유지, 줄이 이미 있으면 건너뜀). WSL에서 빌드 산출물의 복사본에 두 번 연속 돌리면 첫 번째는
`adb on mode=600`, 두 번째는 `adb already on`이고, 원본과의 차이는 덧붙인 한 줄뿐이며 `e2fsck -fn`은 깨끗했다.

새 홈에서 돌린 a15-6(2026-10-03 11:52~11:56 KST)은 드라이버 종료 코드 0이다. 결과 원문은 `dod-a15-6-result.json`에 있다.

```
OME-INSTALL env aaropa
OME-INSTALL step keys 91
OME-INSTALL keys 1
OME-INSTALL adb on mode=600
OME-INSTALL step finish 92
OME-INSTALL done
```

| 단계 | 결과 | 걸린 시간 |
|---|---|---:|
| S1.5 설치(`설치하기` 뒤 사용자 입력 없음) | 통과 | 72.6초 |
| S1.6 첫 부팅과 능력 조사 | 통과 | 120.7초 |
| S1.7 게임 설치, 게임 실행 | 건너뜀(`OME_DOD_SKIP_GAME=1`, 변환기 없는 프로필) | |
| 정지 | 통과 | 4.2초 |

능력 조사 결과는 부팅 표시, 앱 목록, 화면 크기(1280x800), 미디어 볼륨, 스크린샷이 `available`이다. 기기 ID와 전경 앱은
`unknown`, 멀티터치와 네이티브 브리지와 루트는 `unavailable`이다. 네이티브 브리지가 없는 것은 블롭 없는 이미지이므로
기대한 결과다(R3). 첫 부팅 화면은 `images/dod-a15-6-first-boot-probe.png`다.

남은 일: 다음 이미지는 `guest/build/build-image.sh`가 `vendor/extra/product.mk`로 같은 속성을 넣는데, 이 변경은 아직
빌드로 확인하지 않았다. lunch가 `bliss_x86_64-ap4a-userdebug`인데 `ro.build.type=user`, `ro.debuggable=0`이 되는 까닭도
찾지 않았다. adb가 끝내 붙지 않으면 제품이 부팅 시한마다 끄고 다시 띄우기를 끝없이 되풀이하는 문제(a15-5)도 남아 있다.

## 5. 내려받기부터 완주 (a15-7)

a15-6까지는 ISO를 미리 넣어 내려받기를 건너뛰었다. a15-7(2026-10-03 11:59~12:10 KST)은 아무것도 넣지 않은 새 홈에서 돌렸다.
제품이 사전 릴리스 `guest-android-15-20261002`의 1 GiB 조각 셋을 받아 이어 붙이고 대조했다. 드라이버 종료 코드는 0이고
결과 원문은 `dod-a15-7-result.json`이다.

| S1.4 내려받기(2,946,441,216 B, 조각 셋, 평균 7.2 MB/s) | 통과 | 408.1초 |
| S1.5 설치 | 통과 | 75.3초 |

## 6. 이미지에 든 속성 위장 코드와 프로필 회수 (2026-10-03)

빌드 산출물의 `system/build.prop`은 `ro.build.type=userdebug`, `ro.debuggable=1`인데, 실행 중인 게스트는 `ro.build.type=user`,
`ro.debuggable=0`이었다(3절). 원인은 BlissOS가 고친 `system/core/init/property_service.cpp`의 `workaround_snet_properties`다.
복구 모드나 eng 빌드가 아니면 부팅 때마다 다음 값을 강제로 덮어쓴다(주석은 "snet: Hiding sensitive props").

```
ro.boot.vbmeta.device_state=locked   ro.boot.verifiedbootstate=green   ro.boot.flash.locked=1
ro.boot.veritymode=enforcing         ro.boot.warranty_bit=0            ro.warranty_bit=0
ro.debuggable=0  ro.secure=1  ro.build.type=user (system, system_ext, vendor, product, odm 모두)
ro.build.keys=release-keys  ro.build.tags=release-keys  ro.system.build.tags=release-keys
vendor.boot.vbmeta.device_state=locked  vendor.boot.verifiedbootstate=green  sys.oem_unlock_allowed=0
ro.adb.secure=1  ro.force.debuggable=0  (ro.build.flavor의 userdebug도 user로 바꿈)
```

잠긴 판매 기기의 값으로 꾸며 SafetyNet 같은 검사를 속이는 코드다. OME가 쓴 코드는 아니지만 OME가 빌드해 배포하는 이미지에
들어 있으므로 D8(위장과 탐지 회피 금지, 변경 불가)과 R7에 걸린다. 사용자 결정(2026-10-03)으로 0.1.2에서는 안드로이드 15
프로필(`manifests/images/ome-android-15.json`)을 빼고, 이 함수를 끈 이미지를 다시 빌드한 뒤 프로필을 되돌린다. adb가 기본으로
꺼져 있던 것(3절)과 `adb root` 거부도 이 덮어쓰기에서 나온다.
