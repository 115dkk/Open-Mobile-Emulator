# M0 game run, 2026-09-26: findings log

Working notes written while the scenario ran. `metrics.md` holds the numbers,
`environment.md` the harness; this file records what happened and why, in order.
Times are host local (KST). Guest `default`, distribution QEMU 11.1.0, WHPX.

## APK (runbook step 4)

`launcher/Get-GameApk.ps1 -Package com.epidgames.trickcalrevive -DeviceSerial <phone-serial>`
pulled four splits from the user's phone (Samsung SM-S948N, Android 17):
`base.apk`, `split_config.arm64_v8a.apk`, `split_gpdeku.apk`,
`split_gpdeku.config.arm64_v8a.apk`. apksigner reported the expected signer
`e44ffeb582e01d533416db1304e5c2e41f3156c0`; `pulled.json` in
`%LOCALAPPDATA%\OpenMobileEmulator\apks\com.epidgames.trickcalrevive\` has the
hashes. Game version 10644 (`Ver 1.6.44-Production` on the title screen),
minSdk 26, targetSdk 36, Unity 6000.3.13f1, IL2CPP, arm64-v8a only.

## Two boot entries, one disk

GRUB `savedefault` writes the chosen entry to `/boot/grub/grubenv` on the ext4
install partition (vda2). The running guest can rewrite it with `adb root`:

```
mount -t ext4 -o rw,noatime /dev/block/vda2 /data/local/tmp/root
# 1024-byte file: "# GRUB Environment Block\ndefault=<entry>\n" padded with '#'
```

Entry strings (submenu title, `>`, entry title):

- virgl: `VM Options ->> >BlissOS-16.9.7 2024-10-11  - QEMU/KVM - Virgl - SW-FFMPEG`
- software: `VM Options ->> >BlissOS-16.9.7 2024-10-11  - Vbox/VMWare - No HW Acceleration`

`nomodeset-boot-via-grubenv.txt` shows the second boot coming up on the
software entry (`nomodeset HWACCEL=0`, SwiftShader GLES, 1024x768) with no
keystroke at the menu. Mounting with `-o ro` fails with "Device or resource
busy" because the same block device is already mounted rw for `/data`.

## First run under virgl (10:04 to 10:36)

Boot came up on the virgl entry (`HWC=drm_minigbm GRALLOC=minigbm_arcvm`, Mesa
virgl on the RTX 2080 SUPER, 1280x800). `run-virgl-firstlaunch/` is the install
plus first-launch sample: `adb install-multiple` of the four splits succeeded,
the app started, and `game-process-maps.txt` shows `libil2cpp.so`, `libunity.so`
and the other arm64 libraries mapped through `libndk_translation.so` and its
proxy libraries. Unity logged `Scripting Backend 'il2cpp', CPU 'arm64-v8a'` on
`Android OS 13 (API 33)`. `logcat-bridge-errors.txt` is empty.

1. **Intro video is black.** The guest's software codec process aborts the
   moment the game plays its intro (`swcodec-gralloc-abort-virgl.txt`):
   `media.swcodec` in `c2.android.avc.decoder`, `Abort message: 'gralloc-mapper
   is missing'`, from `GraphicBufferMapper` inside `libcodec2_vndk`. Unity then
   logs `Cannot Prepare a disabled VideoPlayer` and a tap skips the video. The
   same abort recurs on every video (download screen, second boot). It is not
   tied to the virgl entry: the software-rendering boot aborts identically.
   Bliss's menu offers `FFMPEG_CODEC=1 FFMPEG_PREFER_C2=1` entries (the
   ffmpeg codec2 service is running); untested, listed as an M1 follow-up.
2. **Title reached** (`step-02-title-loading.png`), then the 5.1 GB data
   download prompt (`step-03-data-download-prompt.png`). Download ran at about
   19 MB/s through slirp.
3. **Relaunching the running game killed it.** `Invoke-GuestTest.ps1` was
   re-run for a metrics sample while the download ran; its `monkey` launch made
   the activity pause and resume, and Android killed the process with
   `ForegroundServiceDidNotStartInTimeException` for
   `.patch.TrickcalPatchService` ("Bringing down service while still waiting
   for start foreground"). The patch service had been started with
   `startForegroundService` but never reached `startForeground`, plausibly
   because the notification permission had been declined at the first prompt.
   Fixes: `-SkipLaunch` added to `Invoke-GuestTest.ps1`, notification permission
   granted with `pm grant ... POST_NOTIFICATIONS` as an ordinary user would.
   This is not a translator or emulator failure.
4. **Translator abort (stop-condition class).** On the relaunch, while the game
   sat on the download prompt, pid 4775 died at 10:16:57:
   `ndk_translation: Cannot process signal 11`, then SIGABRT in `Thread-29`.
   Stack (`crash-ndk-translation-1/tombstone.txt`): `HandleHostSignal` ->
   `ToGuestJNIEnv` <- `DoJavaVMTrampoline_AttachCurrentThread` <- translated
   code in `/memfd:exec`. A native thread attaching to the JVM took a SIGSEGV
   that the translator could not deliver. Seen once in three launches so far;
   the process had been up 170 s. Recorded, not worked around. If it recurs the
   run stops per CLAUDE.md M0.
5. Third launch: download resumed from 0.9 GB and finished (`/sdcard/Android/data`
   grew to 5,468 MB in about three minutes), then the game stayed on the
   "트릭컬로 출발!" loading screen for over ten minutes with one thread busy
   (`step-06-loading-stall-virgl.png`, `run-virgl-loading-stall/`). At that
   point the guest was rebooted into the software entry to separate the codec
   abort from the GPU path; in hindsight the software boot shows this stage
   is a long asset verification (four worker threads at 68 % each), so the
   virgl "stall" was probably the same work with fewer threads busy. Not
   re-measured under virgl yet.

## Network

- `airbridge.io` (the game's attribution SDK) refuses the TLS handshake from
  the guest **and from the Windows host** (`curl` on both: handshake closed by
  the peer; google.com works from both). This is the host network, not the
  emulator. The SDK retries every 60 s; the game proceeds without it.
- The game server socket (`4.230.37.207:29001`) connects and exchanges data.
- Google check-in, Firebase logging and Play Games service calls reach their
  servers. Play Games sign-in returned an error code (uncertified device, no
  account) and the game fell back to its own login screen.

## Afternoon follow-ups (user decisions 15:30): memory, codec entry, frame pacing

- **8 GiB guest** (`Start-Guest.ps1` default is now 8192 MiB, up to 16 GiB
  approved): the run meant for stage 1-3 never entered the battle (1-3 is
  locked; the taps stayed on the stage list, seen only when the screenshots
  were reviewed afterwards), so its numbers are for the stage list screen: the
  same 38 fps as the earlier battle, and MemFree rose from about 100 MB to
  1.46 GB (MemAvailable 4.85 GB) (`run-virgl-8g-battle/`). Its CPU figures
  (game 60 to 64 %, host 14 %) are for the stage list and do not compare with
  a battle; the 60 Hz battle below is the like-for-like 8 GiB number.
- **Why 38 fps.** The guest's only DRM mode on `Virtual-1` is `1280x800` at
  75 Hz (`/sys/kernel/debug/dri/0/state`: pixel clock 107.3 MHz, 1728x828 total;
  SurfaceFlinger `VSYNC period: 13334426 ns`; `dumpsys display` fps=74.99),
  which is QEMU's generated EDID default. The host monitor runs at 59 Hz. The
  game's frames land on every second guest vsync (26.5 ms p50 with p90 within
  4 ms of it), so the presented rate is 37.5 fps: the frame takes between 13.3
  and 26.7 ms, and the 75 Hz grid rounds it up. On top of that, 75 Hz guest
  presents onto a 59 Hz host display cannot be evenly paced, which is a judder
  source independent of the frame rate. A `video=Virtual-1:1280x800@60`
  kernel argument (custom GRUB entry `OME virgl FFMPEG 60Hz`) is the test for
  both: the same frame time would give 60 fps if it is under 16.7 ms and 30 fps
  otherwise.
- **GRUB custom entries.** `/boot/grub/custom.cfg` on vda2 is sourced by
  Bliss's `android.cfg` after `add_entry` is defined, so extra entries need no
  edit of the shipped config. Top-level entries save to grubenv as their bare
  title (`BlissOS-16.9.7 2024-10-11  - OME virgl FFMPEG`; `$live` is empty on
  an installed disk, hence the double space).
- **Codec entry test (fifth boot, 15:46).** Booting the custom entry with the
  shipped menu's `FFMPEG_CODEC=1 FFMPEG_PREFER_C2=1` changed nothing: Bliss's
  `/system/etc/init.sh` reads `FFMPEG_CODEC2_PREFER`, so the ffmpeg codec2
  service kept rank 4294967295 and the game's MediaCodec still picked
  `c2.android.avc.decoder`, whose process aborted as before. With
  `setprop debug.ffmpeg-codec2.rank 0` and a restart of `media` (mediaserver
  caches the codec list; restarting only the ffmpeg service was not enough)
  the game created `c2.ffmpeg.h264.decoder` and `c2.ffmpeg.aac.decoder`, no
  process aborted and MediaCodec reported no error. The intro still showed
  black, so the remaining break is between the decoder's output buffers and
  Unity's external texture under virgl, not the decoder. `custom.cfg` now
  carries `FFMPEG_CODEC2_PREFER=1` so the rank is right from boot.
- **Sixth boot (15:55), `FFMPEG_CODEC2_PREFER=1` from boot plus
  `video=Virtual-1:1280x800@60`.** The kernel argument changed nothing: the
  only mode stayed the EDID's 1280x800 at 75 Hz (`dumpsys display` fps=74.99).
  The ffmpeg decoders were created from the first launch and nothing aborted,
  but the game's SurfaceView stayed black after the intro and after taps while
  still presenting 127 frames per 5 s, so with the ffmpeg path the intro's
  black frame persists instead of being skipped. The swcodec-abort path is the
  lesser problem (black only during the intro), so the standard virgl entry is
  restored as the saved default; the custom entries stay in `custom.cfg` for
  later work on the video-to-texture path. The distribution QEMU's
  `virtio-vga-gl` exposes `edid`, `xres`, `yres` and no refresh-rate property,
  so the next test is `-global virtio-vga-gl.edid=off`, which makes the guest
  driver fall back to a 60 Hz CVT mode.
- **Seventh boot (16:10), standard virgl entry, QEMU started with
  `-global virtio-vga-gl.edid=off` (8 GiB).** Without the generated EDID the
  guest's only mode is a CVT 1280x800 at 60 Hz (`dumpsys display` fps=59.96,
  SurfaceFlinger VSYNC period 16.68 ms). The game then presents 58 fps at the
  title, in the lobby and on the stage list screen (the files named `setup`
  and `wave` are the stage list, stage 1-3 being locked), frame time p50
  16.8 to 17 ms, p99 under 25 ms (`run-virgl-60hz-battle/`), against 38 fps and
  26.5 ms on the same screens under the 75 Hz mode. A 60 Hz battle number is
  still owed. The game's frame
  fits in a 60 Hz vsync and not in a 75 Hz one, which is the whole difference;
  the host monitor at 59 Hz now receives one guest frame per refresh instead of
  a 75-on-59 cadence. Game process CPU rose to 92 % of one vCPU with the
  higher frame count. This becomes the launcher default for the virgl GPU
  option. Note for the runbook: `Start-Guest.ps1 -ExtraArgs @(...)` must be
  called in-process; `pwsh -File` flattens the array and the second element
  lands in `-Accel`.
- **Eighth measurement, same seventh boot (16:20 to 16:38): the real 1-3
  battle at 60 Hz.** Tapping the locked stage shows "이전 단계부터 차근차근
  와주세요~!"; the missing step was the reward node between 1-2 and 1-3 (a
  200-elif chest that has to be opened by hand). After that 1-3 unlocked. Its
  deck screen and its battle carry another tutorial, which pauses on
  highlighted buttons and dialogue; 건너뛰기 (top right on the deck screen, top
  left in battle) clears it. Active wave 1 with no overlay: 58.5 fps, p50 17 ms,
  p90 20.6, p99 28 (`sf-latency-battle13-wave-clean.txt`,
  `step-53-virgl-60hz-battle-1-3-wave1.png`); with the tutorial dialogue over
  the field 54.3 and 57.5 fps. Game process 120 to 140 % of a vCPU, host CPU
  24 %, PSS 2.05 GB, guest MemFree 1.53 GB. Victory, player Lv.3 to Lv.4
  (`step-55-...-end.png`). `virtio-vga-gl,edid=off` is now the launcher's
  virgl device string.

## Host bugcheck history (for the reboot investigation)

`Get-WinEvent` on the System log lists five `0x000000D1`
(DRIVER_IRQL_NOT_LESS_OR_EQUAL) bugchecks since 2026-09-03: 09-03 02:44,
09-05 20:26, 09-05 20:41, 09-25 10:32 and 09-26 13:05. The user analysed the
two surviving minidumps separately (folder `AhnLab_BSOD_20260926` on their
Desktop, with `!analyze -v` output and a vendor report): both fault in
`NETIO!StreamInvokeCalloutAndNormalizeAction` (+0x5C and +0x239, the two
offsets that recur in the event log) while the WFP stream layer classifies
loopback TCP data re-injected by a worker thread, and AhnLab's network filter
driver `AMonCDW8.sys` (V3 365 Clinic 4.17, driver 10.11.0.2) is the callout on
the stack in both dumps. Three of the five crashes happened in Modern Standby.
The first three predate this project and the 09-25 one predates the guest, so
the emulator is not the trigger, but the guest adds loopback TCP of its own
(adb and QMP over `127.0.0.1` host forwards), which is the same path. The
user's decision on V3 is outside this repository; the dump type on the host
was switched to a kernel memory dump for the next occurrence.
