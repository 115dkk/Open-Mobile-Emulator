# Experiment: four-processor cpuinfo view for ARM code, 2026-09-26 (host clock)
# Guest: Bliss 16.9.7, libndk_translation 0.2.3, 4 vCPU, virgl entry with edid=off, 8 GiB (QEMU pid 2344, booted 16:10).

## Why

Unity logged `SystemInfo CPU = x86-64, Cores = 2` on the 4-vCPU guest. The cause is
`/system/etc/cpuinfo.arm64.txt` (403 bytes, two `processor` blocks); libnativebridge
bind-mounts it over `/proc/cpuinfo` in every ARM app's mount namespace
(`/proc/<game pid>/mountinfo`: `/system/etc/cpuinfo.arm64.txt /proc/cpuinfo ... master:1`).
The question was whether a four-processor view changes the game's threading or frame rate.

## Procedure

1. `/data/local/tmp/cpuinfo.arm64.4.txt`: the stock file plus copies of the two blocks
   renumbered 2 and 3.
2. `mount --bind /data/local/tmp/cpuinfo.arm64.4.txt /system/etc/cpuinfo.arm64.txt` from
   `adb shell` (root, SELinux permissive). The root mount is `shared:1`, so the bind
   propagated to zygote64 (pid 855) and to apps started afterwards.
3. `am force-stop`, relaunch with `monkey`, read the Unity SystemInfo lines, list thread
   names, replay stage 1-3 with a fixed tap timing and take SurfaceFlinger windows.
4. Control: remove the bind mount, relaunch, same replay and timing.

## Conclusion

The core count the translator presents does not change the game's frame rate, frame-time
distribution or thread inventory on this guest; CPU use was slightly higher with four
processors visible. The stock `cpuinfo.arm64.txt` stays and nothing changes in the launcher
or the guest. `Cores = 2` in the Unity log is cosmetic here.

## Notes for anyone repeating this

- The bind mount is replicated by shared propagation (root `shared:1`, `/data` `shared:4`):
  twelve mount entries referenced the four-processor file afterwards, on
  `/system/etc/cpuinfo.arm64.txt`, `/proc/cpuinfo` and the file itself. A plain `umount`
  answered "Device or resource busy" and left the game seeing four processors on the next
  launch; `umount -l /system/etc/cpuinfo.arm64.txt` removed them all. A future overlay would
  mount with `--make-private` first, or replace the file in the image.
- 18:47:05 relaunch after the first, incomplete umount still showed `Cores = 4`; that launch
  is not part of the comparison.
